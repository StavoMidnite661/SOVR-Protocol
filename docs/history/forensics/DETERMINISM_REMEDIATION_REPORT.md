## 2. Deterministic Timestamp Mechanism Selected — and Why

**Canonical Compilation Timestamp (CCT):** `2026-08-07T00:00:00.000Z`, defined once in `packages/compiler/src/utils/deterministic-time.ts` and used identically for `compiled_at`, scenario `integrity.timestamp`, simulation registry `integrity.timestamp`, and all 15 registry `integrity.timestamp` blocks.

Why this mechanism:
1. **Required fields preserved.** Every ABI/type contract keeps its REQUIRED `string` timestamp field (§1 non-negotiables intact).
2. **Not invented from hash bytes, not a wall-clock reading.** It is a fixed, documented ISO-8601 UTC constant — a canonical provenance point denoting "the compilation", satisfying the FROZEN ABI description "ISO-8601 timestamp of compilation" in its deterministic form.
3. **Traceable canonical source.** The value is the repository's pre-existing deterministic time origin already established in `packages/runtime/src/simulation/deterministic.ts` (`baseTime`), so it derives from an explicitly documented in-repo canonical constant rather than an arbitrary new number.
4. **Documented in the compiler contract.** `compiler/BUILD_MANIFEST.yaml → timestamp_policy.canonical_generated_at` (value, semantics, guarantees, application scope) realizes the existing `generated_at_field: omitted_or_canonical_only` policy via its "canonical" branch — no weakening of R5/R9.
5. Satisfies all nine directive requirements: valid ISO-8601; identical for identical inputs; independent of host clock, timezone, environment, filesystem order, execution time, and randomness; documented canonical source.

The alternative — a hash-derived pseudo-date — was rejected because the directive prohibits fabricating timestamps from hashes and no repository evidence assigns time semantics to any hash.
