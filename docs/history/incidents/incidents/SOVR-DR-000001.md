# SOVR Incident Report

**INCIDENT-ID:** SOVR-DR-000001  
**Title:** TigerBeetle Ledger Instance Loss Event  
**Classification:** Development Environment Recovery — Accounting Truth Layer  
**Impact:** Ledger runtime unavailable; data preserved  
**Date:** 2026-08-06  
**Author:** SOVR Engineering  
**Status:** OPEN — Ledger Provenance Unresolved. Multiple TigerBeetle clusters discovered. Recovery path paused pending forensic identification of authoritative ledger instance.  

---

## 1. Executive Summary

The TigerBeetle ledger instance (`SOVR-TREASURY-001`) serving as the Accounting Truth Layer for the SOVR Financial OS Protocol experienced a runtime loss event. Initial assessment indicated the instance process/container state was removed, but the underlying ledger data files remained intact on the D:\ volume.

Forensic investigation has revealed **multiple TigerBeetle environments** on the system:

1. **INSTANCE-001** (`sovrb-tb-instance`): Single-replica cluster, cluster_id=0, configured as the SOVR instance with genesis scripts and account definitions. Contains only 1 account (ID: 1) instead of the expected 13 SOVR reference accounts.
2. **INSTANCE-002** (`Tigerbeetle/data/`): 3-replica cluster, cluster_id=0, with 9,542 commits and activity through July 2026. No SOVR application references found. Contains upstream TigerBeetle source and Mojaloop reference projects.

The incident is now classified as **ledger provenance unresolved**. Recovery is paused pending determination of which cluster represents the historical SOVR Accounting Truth Layer.

The incident exposes a critical architectural gap: the absence of a formal Ledger Continuity Certification framework for deterministic financial state recovery and provenance identification.

## 6. Root Cause Analysis

### 6.1 Probable Cause

The TigerBeetle instance was removed via one of the following:

```powershell
# Likely commands executed by the agent:
docker rm sovrb_tb                    # Scenario A
docker-compose down                   # Scenario A
Remove-Item -Recurse tigerbeetle_data # Scenario B (data intact suggests not this)
```

### 6.2 Contributing Factors

1. **No infrastructure-as-code guardrails** — No Terraform/Pulumi preventing manual destruction
2. **No automated backup policy** — Backup file exists but no scheduled rotation
3. **No Ledger Continuity Certification** — Missing `packages/certification/ledger-continuity/` artifacts
4. **Agent autonomy gap** — Agent was not constrained from modifying infrastructure state

## 8. Recovery Plan

### 8.1 Recovery Sequence

```
Step 1: Preserve Evidence
Step 2: Verify Cluster ID
Step 3: Restart Ledger Instance
Step 4: Validate Account State
Step 5: Resume Operations
Step 6: Document Incident
```

### 8.2 Step 1 — Preserve Evidence

```powershell
# Create forensic copy of ledger data
$timestamp = Get-Date -Format "yyyyMMdd-HHmmss"
$backupDir = "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\forensic-backup-$timestamp"
New-Item -ItemType Directory -Path $backupDir
Copy-Item "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\tigerbeetle_data\0_0.tigerbeetle" "$backupDir\"
Copy-Item "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\tigerbeetle_data\0_0.tigerbeetle.bak" "$backupDir\"
Copy-Item "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\.env.example" "$backupDir\"
Copy-Item "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\docker-compose.yml" "$backupDir\"
```

### 8.3 Step 2 — Verify Cluster ID

The cluster ID must match the existing ledger file. Expected value: `0`.

```powershell
# Inspect .env.local if it exists
Get-Content "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\.env.local" -ErrorAction SilentlyContinue
```

If `.env.local` does not exist, create it:

```powershell
Copy-Item "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\.env.example" "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance\.env.local"
```

**CRITICAL:** Do NOT change `TB_CLUSTER_ID`. A mismatched cluster ID will cause TigerBeetle to reject the existing ledger file.

### 8.4 Step 3 — Restart Ledger Instance

**Option A: Native Binary (Recommended for Windows)**

```powershell
cd "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance"
.\tigerbeetle.exe start --addresses=0.0.0.0:3000 tigerbeetle_data/0_0.tigerbeetle
```

**Option B: Docker Compose**

```powershell
cd "D:\sovr-financial-os-protocol-v1.0.0\sovrb-tb-instance"
docker-compose up -d
```

### 8.5 Step 4 — Validate Account State

```powershell
# Test connection
npx tsx test-tb-connection.ts

# Run genesis verification (idempotent)
npx tsx src/scripts/genesis.ts
```

Expected output:
```
[Genesis] Connecting to TigerBeetle cluster...
[Genesis] Creating 10 reference accounts...
[Genesis] Created: 0, Already existed: 10, Failed: 0
[Genesis] Looked up 10 accounts.
[Genesis] Genesis complete: SOVR-COMMERCIAL-SETTLEMENT-000001
```

### 8.6 Step 5 — Resume Operations

```powershell
# Start backend gateway
npm run server

# Verify health
curl http://localhost:3001/api/health
```

### 8.7 Step 6 — Document Incident

Create formal incident record in `docs/incidents/SOVR-DR-000001.md`.

## 11. Conclusion

This incident is **recoverable without data loss**. The TigerBeetle ledger data files are intact. The correct recovery path is to restart the existing instance using the preserved data, not to create a new instance.

The incident serves as a critical validation of the SOVR protocol's design principle: **"Truth is mechanical, not narrative."** The protocol specifications, account definitions, and genesis scripts survive regardless of runtime state.

The missing Ledger Continuity Certification framework must be addressed before production deployment to ensure deterministic financial state recovery under all failure modes.
